# Сборка core

После `bash scripts/setup.sh` запустите из корня проекта:

```bash
bash scripts/build_core.sh
```

Все операции выполняет сохранённый SQL. Скрипт shell только объединяет
SQL-файлы и передаёт их `psql` внутри контейнера. Для подключения своим
локальным `psql` можно выполнить главный файл напрямую:

```bash
psql -X 'postgresql://hack:hack@localhost:5432/marketplace' -f model/build.sql
```

## Файлы

- `build.sql` — транзакция, блокировка параллельной сборки и порядок выполнения.
- `tables.sql` — таблицы, ограничения, индексы.
- `load.sql` — загрузка справочников, фактов и расчёт итогов.
- `quality.sql` — запись предупреждений в `core.dq_issue`.
- `checks.sql` — обязательные проверки перед `COMMIT`.

Повторный запуск полностью обновляет только перечисленные в `build.sql`
таблицы модели. `raw`, `mart` и посторонние таблицы не меняются. Если загрузка
или проверка завершается ошибкой, транзакция откатывается целиком, включая
очистку старого core. Это полная пересборка, не миграция схемы: изменение
структуры существующих таблиц требует отдельного `ALTER TABLE`.

## Уровни данных

| Таблица | Одна строка | Ключ |
|---|---|---|
| `dim_customer` | Человек | `customer_key` = `customer_unique_id` |
| `fct_order` | Заказ | `order_id` |
| `fct_order_seller` | Часть заказа одного продавца | `(order_id, seller_id)` |
| `fct_order_item` | Одна единица товара в заказе | `(order_id, order_item_id)` |
| `fct_payment` | Запись оплаты | `(order_id, payment_seq)` |
| `fct_review` | Анкета отзыва | `review_id` |
| `fct_review_order` | Связь анкеты с заказом | `(review_id, order_id)` |

Остальные справочники: `dim_date`, `dim_category`, `dim_product`,
`dim_seller`, `dim_order_status`, `dim_payment_type`.

## Принятые правила

- Структура следует обсуждаемой диаграмме. Итоги заказа, покупателя и части
  заказа продавца сохранены физически и полностью пересчитываются при сборке.
  Проверки сверяют денежные итоги заказа и продавца с деталями.
- Адресные атрибуты покупателя сохраняются в заказе вместе с исходным
  `source_customer_id`. Почтовый индекс дополняется нулями до пяти цифр;
  исходный формат проверяйте `scripts/profile_raw.sql` перед загрузкой.
- Очистка городов: нижний регистр, удаление крайних и повторных пробелов.
  Разные написания одного города автоматически не объединяются.
- Категории собираются из товаров и переводов. `unknown` означает отсутствие
  категории; `pt:` перед именем предотвращает конфликт с реальным названием.
  Отсутствие перевода не превращает известную категорию в неизвестную.
- `fct_order_seller` не представляет физическую посылку. Его срок отгрузки —
  минимальный срок позиций. Дополнительно срок сохранён в каждой позиции;
  разные сроки одной пары заказ/продавец записываются в журнал качества.
- Повторяющийся `review_id` объединяется только при одинаковых исходных
  атрибутах. Различающиеся атрибуты останавливают сборку. Связи с заказами
  сохраняются все. Для оценки заказа выбирается последний ответ, затем
  последняя дата создания, затем максимальный `review_id` при равенстве дат.
  Это детерминированное аналитическое правило, не утверждение о бизнес-процессе.
- `is_revenue` означает включение статуса `delivered` в отчёт продаж. Формулу
  суммы и временной период нужно определить в конкретном отчёте.
- Нет платежей: `paid_amount IS NULL`; нет позиций: количество и суммы равны
  нулю. Это не означает, что отсутствие платежа эквивалентно бесплатному заказу.
- Нулевые вес, рассрочка и платежи, аномальная хронология сохраняются и
  отмечаются в `dq_issue`. Обязательных ограничений порядка дат нет.
- Невалидные типы, дубли первичных ключей, потерянные обязательные ссылки и
  нарушения строгих ограничений останавливают сборку без потери старого core.
  Сборка не пропускает ошибочные строки молча и не исправляет их догадками.
- Календарь покрывает полные годы всех исходных дат. `purchase_date` имеет FK
  на календарь. Остальные timestamp сохраняют время; для календарных срезов
  соединяйте их `::date` с `dim_date.date_key`.

Не соединяйте позиции, платежи и отзывы напрямую для суммирования: сначала
агрегируйте каждый набор до уровня заказа. Наличие ключей не защищает от
размножения сумм при соединении нескольких связей «один ко многим».

## Посмотреть результат

```sql
SELECT * FROM core.fct_order LIMIT 10;
SELECT check_id, count(*) FROM core.dq_issue GROUP BY 1 ORDER BY 2 DESC;
SELECT * FROM core.dq_issue WHERE check_id = 'payment_items_mismatch' LIMIT 10;
```
