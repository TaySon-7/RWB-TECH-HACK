# Capibara: ClickHouse + Kafka + Protobuf + Grafana

Базовая архитектура слита в `main`. Расширение коммерческого дашборда — `feture/sales-dashboard-readme`.

## Запуск

```bash
bash scripts/analytics.sh up
python3 scripts/smoke_analytics.py
```

Открыть http://localhost:3000/d/capibara-commerce. Пользователь `admin`,
пароль — `GRAFANA_ADMIN_PASSWORD` в `.env.analytics`. Этот файл создаётся
автоматически с правами 0600, не коммитится и не перезаписывается при деплое.
По умолчанию Grafana слушает только localhost. На выделенном сервере
`deploy/deploy.sh` также сохраняет localhost binding; публичный доступ
включается отдельно после согласования. Для просмотра используется SSH-туннель.
Kafka и ClickHouse не публикуют порты на хост.

Для жюри автоматически создаётся отдельный пользователь `jury` с ролью Viewer.
Пароль — `GRAFANA_VIEWER_PASSWORD` в том же файле. Администраторские доступы
жюри не требуются. Повторный деплой не меняет пароли существующих пользователей.

Исходный PostgreSQL-стенд в `docker-compose.yml` сохранён для воспроизведения
первоначальной модели и сверки. Новый Compose полностью независим, его
контейнеры и тома имеют префикс `rwb-analytics`. В новом runtime PostgreSQL нет.

## Путь данных

```text
8 исходных CSV
    → Python producer: типизация, контроль денежных значений
    → ProtobufSingle: schemas/marketplace.proto
    → Kafka: 8 топиков × 3 партиции, LZ4, ключ = естественный ключ строки
    → встроенные Kafka consumers ClickHouse
    → materialized views → raw (ReplacingMergeTree)
    → core (канонические представления с FINAL)
    → проверки связей, количества строк и денежных итогов
    → атомарная публикация mart.sales_daily
    → Grafana: пользователь с SELECT только на mart
```

Нативные consumers ClickHouse действительно декодируют бинарный Protobuf.
HTTP используется для DDL, проверок и публикации витрин; исходные строки
не обходят Kafka. `pipeline/schema.py` задаёт соответствие CSV / Protobuf /
ClickHouse. `python3 pipeline/generate_schema.py --check` проверяет актуальность
сгенерированных контрактов. Схемы доступны producer и ClickHouse из одной версии
репозитория. При развитии протокола нельзя переиспользовать номера полей;
несовместимое изменение требует нового контракта/топика v2.

Суммы передаются целыми сентаво, а в `core` представлены Decimal. Float
используется только для вывода в Grafana. Исходные временные значения не имеют
часового пояса: кодирование в миллисекунды сохраняет wall-clock время без
преобразования бразильских локальных дат. Пустая дата = 0 в контракте и NULL в
`core`; отсутствующие числовые атрибуты товара = -1 в контракте и NULL в `core`.

## Повторная доставка и публикация

Kafka обеспечивает доставку как минимум один раз. Producer использует
идемпотентную отправку, но между записью ClickHouse и коммитом Kafka offset
возможны дубли. Поэтому `raw` хранится в ReplacingMergeTree с `source_version`,
а канонические представления всегда используют FINAL. Денежные суммы не
зависят от того, успели ли произойти фоновые слияния.

`bash scripts/analytics.sh replay` повторно отправляет тот же снимок и
проверяет, что все строки актуальной версии дошли, а суммы не изменились.
Каждый успешный импорт сохраняет hash источника, размеры сообщений и время
в `ops.load_runs`. Повторный обычный deploy не отправляет неизменившийся снимок.

Текущий importer предназначен для полного неизменяемого снимка Olist.
Он явно отклоняет замену уже загруженного снимка другим: удалённые строки
нельзя корректно учесть одним upsert. Для изменяемых источников нужно добавить
CDC-события удаления, версии источника и управляемую публикацию batch watermark.
Частично завершённая первая загрузка повторяется безопасно.

Витрина публикуется пакетно после проверок, а не на каждое Kafka-сообщение:
`EXCHANGE TABLES` меняет проверенный снимок целиком. Пока идут загрузка и
проверки, пользователи читают предыдущую витрину. Отдельные запросы панелей
в момент публикации могут попасть на разные версии; для строгого снимка
всего экрана потребуется фиксированный publication_id в запросах.

Период по умолчанию: оформление с 2016-09-01 по 2018-08-31 включительно.
Только `delivered`, валюта BRL. Суммы рассчитаны по позициям своих заказов,
без прямого соединения позиций, платежей и отзывов.

## CI/CD

`.github/workflows/analytics.yml` запускается на push в рабочую ветку и main,
а также на pull request в main. CI поднимает чистый стенд, пропускает весь
датасет через Kafka/Protobuf, сверяет показатели и выполняет replay.
Деплой после успешного CI выполняется только для push/workflow_dispatch,
не для pull request. SSH host key закреплён, параллельные деплои сериализованы.
На сервер передаётся точный проверенный checkout без секретов и исходных CSV.

GitHub Actions Secrets:

- `DEPLOY_HOST`: адрес сервера;
- `DEPLOY_USER`: SSH-пользователь;
- `DEPLOY_SSH_KEY`: отдельный приватный ключ деплоя;
- `DEPLOY_KNOWN_HOSTS`: проверенная запись host key сервера.

Каталог сервера: `/home/fedya/rwb-tech-hack/app`. Данные и конфигурация
сохраняются в именованных Docker volumes и `.env.analytics`. Деплой не удаляет
тома. Полная автоматическая отмена миграций схемы не реализована; перед
несовместимыми изменениями требуется резервная копия и план миграции.

## Демо для защиты

1. Открыть `/d/capibara-commerce?kiosk`: показать две суммы и определения.
2. Выбрать один месяц: суммы и динамика пересчитываются из ClickHouse.
3. Показать ноябрь 2016: ноль сохранён календарём.
4. Запустить `bash scripts/analytics.sh replay`: события проходят Kafka ещё раз,
   а суммы не удваиваются.
5. Показать `ops.load_runs`: фактический размер Protobuf против эквивалентного
   JSON до компрессии. Это измерение размера payload, не доказательство
   ускорения CPU или всей цепочки. LZ4 отдельно сжимает Kafka batches.

## Масштабирование

Текущий стенд — один сервер, один Kafka broker (replication factor 1), один
ClickHouse. Это распределение обработки по партициям, а не отказоустойчивый
кластер. При росте: 3 Kafka brokers с RF=3 и min.insync.replicas=2; ClickHouse
реплики/шарды с корректным распределением ключей; consumers масштабируются в
пределах числа партиций. Настройки ORDER BY и число партиций меняются по
замерам нагрузки. Прежде чем расширять инфраструктуру, измеряем ingestion lag,
время публикации, p95 запросов, память и размер Kafka log.
